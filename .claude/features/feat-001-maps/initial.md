# Раздел «Места»

## 1. Цель

Добавить в приложение отдельный раздел **«Места»** — общую интерактивную карту мест, которые пара посещала или хочет посетить.

Раздел должен сочетать:

- карту с точками;
- поиск реальных заведений и мест;
- собственные оценки и заметки пары;
- историю посещений;
- список любимых мест;
- список желаемых мест;
- рекомендации, куда стоит вернуться;
- статистику и сортировку.

Главная идея:

> **«Где мы были → как нам понравилось → куда хотим сходить → куда стоит вернуться».**

Раздел должен ощущаться как личная карта совместной жизни пары, а не как ещё один Google Maps-клон.

---

# 2. Основные сценарии

Пользователь должен иметь возможность:

1. Найти реальное место через поиск.
2. Добавить его в приложение.
3. Отметить место как:
   - «Хотим посетить»;
   - «Были».
4. Добавить место вручную через точку на карте.
5. Для посещённого места указать:
   - дату посещения;
   - общую сумму расходов;
   - личную оценку каждого партнёра;
   - личное желание вернуться;
   - общую заметку;
   - дополнительные теги/категорию.
6. Посмотреть все места на карте.
7. Переключиться на список.
8. Сортировать и фильтровать места.
9. Получить рекомендации:
   - куда стоит вернуться;
   - какие места понравились обоим;
   - какие места давно не посещали;
   - какие желаемые места находятся рядом.
10. Открыть карточку места и увидеть всю историю посещений.

---

# 3. Навигация

Добавить новый основной раздел:

**📍 Места**

Он должен быть доступен наравне с существующими разделами приложения.

Не создавать отдельный аккаунт, регистрацию или новый тип авторизации.

Раздел использует существующую общую учётную запись и существующую Firebase-инфраструктуру.

---

Основной экран раздела состоит из двух связанных частей:

### Карта

Большая интерактивная карта с точками.

### Список

Список сохранённых мест рядом с картой или под ней в зависимости от размера экрана.

На desktop желательно:

```text

├───────────────┬─────────────────────────────┤
│               │                             │

│ Cafe Y        │   📍                        │
```

На mobile:

- карта;
- переключатель `Карта / Список`;
- поиск сверху;
- карточки мест в нижней части или отдельном режиме.

---

# 5. Поиск мест

Не реализовывать собственную базу заведений.

Использовать внешний Places API / Maps API.

Предпочтительно использовать:

- Google Maps Platform / Places API;
- либо Mapbox, если существующая инфраструктура проекта уже использует Mapbox.

Перед реализацией проверить ограничения существующего проекта и выбрать наиболее простой и экономичный вариант.

Поиск должен позволять найти:

- рестораны;
- кафе;
- бары;
- магазины;
- кинотеатры;
- музеи;
- парки;
- достопримечательности;
- любые другие реальные места.

При выборе результата получать как минимум:

- название;
- координаты;
- адрес;
- внешний `placeId`;
- категорию, если доступна;
- ссылку на внешний источник, если доступна.

---

# 6. Не дублировать внешнюю базу

Не хранить в Firestore полный объект Google/Mapbox Place без необходимости.

В собственной БД хранить только необходимые данные:

- внешний `placeId`;
- собственные данные пары;
- минимальные данные, необходимые для отображения и стабильной работы.

Если внешний API позволяет повторно получать актуальную информацию по `placeId`, использовать этот механизм.

Не создавать собственную копию огромной базы заведений.

---

# 7. Добавление места

После выбора места пользователь должен увидеть форму:

## Добавить место

**Название**

Подтягивается автоматически.

**Адрес**

Подтягивается автоматически.

**Категория**

Например:

- ресторан
- кафе
- бар
- кино
- музей
- парк
- магазин
- другое

**Статус**

- 💭 Хотим посетить
- 📍 Были

Если выбрано «Были», показать дополнительные поля:

- дата посещения;
- сумма расходов;
- оценка Павла;
- оценка Милы;
- желание Павла вернуться;
- желание Милы вернуться;
- комментарий.

---

# 8. Оценки

Использовать шкалу от 1 до 10.

У каждого партнёра две независимые оценки:

### Впечатление

> Насколько тебе понравилось место?

### Вернуться

> Насколько тебе хочется прийти сюда снова?

Например:

```text
Павел
Впечатление      8/10
Вернуться        7/10

Мила
Впечатление      9/10
Вернуться        10/10
```

Не хранить только одну общую оценку.

Индивидуальные оценки важны для последующих рекомендаций.

---

# 9. Общая оценка

Общую оценку можно рассчитывать автоматически:

```text
overallRating =
  (pavelRating + milaRating) / 2
```

Аналогично:

```text
returnScore =
  (pavelReturnScore + milaReturnScore) / 2
```

Не давать пользователю вручную редактировать эти агрегированные значения.

---

# 10. История посещений

Одно место может быть посещено несколько раз.

Не создавать новую сущность места при каждом посещении.

Например:

```text
Stereobar

Посещения:

14.09.2026
Павел: 8
Мила: 9
Потрачено: 6840 ₽

03.05.2026
Павел: 9
Мила: 8
Потрачено: 5200 ₽
```

Поэтому желательно разделить:

```text
Place
Visit
```

### Place

Содержит информацию о самом месте.

### Visit

Содержит информацию о конкретном посещении.

Это позволит:

- хранить историю;
- считать средние оценки;
- анализировать расходы;
- определять, как давно были в месте;
- рекомендовать повторное посещение.

---

# 11. Рекомендуемая модель данных

Пример:

```ts
type Place = {
  id: string

  provider: 'google' | 'mapbox' | 'manual'
  providerPlaceId?: string

  name: string
  address?: string

  latitude: number
  longitude: number

  category?: PlaceCategory

  status: 'visited' | 'want-to-visit'

  notes?: string

  createdAt: Timestamp
  updatedAt: Timestamp
}
```

Отдельно:

```ts
type PlaceVisit = {
  id: string
  placeId: string

  date: Timestamp

  spent?: number

  pavelRating?: number
  milaRating?: number

  pavelReturnScore?: number
  milaReturnScore?: number

  notes?: string

  createdAt: Timestamp
  updatedAt: Timestamp
}
```

Если в существующем проекте уже есть подходящая структура, адаптировать её вместо создания дублирующей модели.

---

# 12. Категории

Минимальный набор:

```ts
type PlaceCategory =
  | 'restaurant'
  | 'cafe'
  | 'bar'
  | 'cinema'
  | 'museum'
  | 'park'
  | 'shop'
  | 'entertainment'
  | 'other'
```

Архитектуру сделать расширяемой.

Не привязывать бизнес-логику к конкретным категориям.

---

# 13. Статусы

Минимально:

```text
💭 Хотим посетить
📍 Были
```

В будущем можно добавить:

```text
❤️ Любимое
🔄 Хотим вернуться
```

Но `любимое` и `хотим вернуться` предпочтительно вычислять из оценок, а не хранить вручную, если это не требуется UX.

---

# 14. Карта

На карте отображать:

### Посещённые места

Обычный marker.

### Желаемые места

Другой визуальный стиль marker.

### Любимые

Можно дополнительно выделять.

Не использовать слишком много разных цветов и иконок.

Карта должна оставаться визуально спокойной.

При клике на marker:

- открыть краткую карточку;
- показать название;
- категорию;
- общую оценку;
- оценку желания вернуться;
- кнопку открытия полной карточки.

---

# 15. Кластеризация

Если мест станет много, использовать clustering.

Например:

```text
      (12)
       ●
```

Вместо десятков overlapping markers.

Не реализовывать clustering вручную, если используемый Maps SDK уже предоставляет готовое решение.

---

# 16. Список мест

Список должен поддерживать:

### Сортировку

- по общей оценке;
- по желанию вернуться;
- по последнему посещению;
- по количеству посещений;
- по потраченным деньгам;
- по дате добавления.

### Фильтры

- были;
- хотим посетить;
- любимые;
- рядом;
- категория;
- оценка;
- город.

---

# 17. Топ мест

Добавить быстрые представления:

### ❤️ Любимые

Места с высокой средней оценкой.

### 🔄 Стоит сходить ещё раз

Места с высоким `returnScore`.

### 👨‍❤️‍👨 Нравится обоим

Места, где обе индивидуальные оценки высокие.

### 🕐 Давно не были

Места с высоким рейтингом, которые давно не посещались.

### 💭 Хотим посетить

Список желаний.

---

# 18. Рекомендации

Создать простой recommendation score.

Не использовать ML на первом этапе.

Например:

```ts
recommendationScore =
  overallRating * 0.4 +
  returnScore * 0.4 +
  recencyScore * 0.2
```

При этом можно дополнительно учитывать:

- сколько времени прошло с последнего посещения;
- насколько высоки обе индивидуальные оценки;
- количество посещений;
- расстояние до пользователя/текущей карты;
- категорию;
- стоимость.

Главная рекомендация:

> **Не усложнять алгоритм на MVP.**

Простая прозрачная формула лучше, чем псевдо-AI.

# 21. Связь с существующими разделами

Раздел «Места» должен интегрироваться с уже существующими сущностями.

### Идеи

Идея может ссылаться на конкретное место.

Например:

```text
💡 Сходить в Stereobar
```

После посещения идею можно преобразовать в посещение места.

### Бюджет

Расход, связанный с посещением, может ссылаться на `visitId`.

Например:

```text
Stereobar
14.09
6840 ₽
```

При этом не обязательно автоматически создавать финансовую операцию без явного действия пользователя.

Предложить кнопку:

**«Добавить расход в бюджет»**

### Дела

Можно создать задачу:

> Забронировать столик в Stereobar

### Календарь

Будущее посещение можно связать с событием.

# 23. Ручная точка

Пользователь должен иметь возможность поставить собственную точку на карте.

Это важно для:

- красивого места без конкретного Place API;
- смотровой площадки;
- места прогулки;
- пляжа;
- конкретной точки на природе;
- места, которое API не знает.

Для ручной точки:

```text
Название
Координаты
Категория
Дата
Оценки
Комментарий
```

`provider = manual`.

---

# 24. Приватность и безопасность

Это критично.

Данные раздела являются приватными.

Использовать существующие Firebase Authentication + Firestore Security Rules.

Никаких публичных страниц мест.

Никакого публичного профиля пары.

Нельзя получить список мест без авторизации.

Проверить Firestore Rules после добавления новых коллекций.

Если используется внешний Maps/Places API:

- API key не должен давать лишних прав;
- ограничить API key по домену;
- включить только необходимые API;
- не помещать секретные ключи в Firestore.

---

# 25. Производительность

Не загружать все данные без необходимости, если количество посещений станет большим.

На первом этапе допустимо простое получение списка.

При росте количества данных предусмотреть:

- pagination;
- lazy loading;
- clustering;
- кэширование данных Places API;
- debounce поиска;
- ограничение запросов к Places API.

Поиск Places API обязательно делать с debounce.

Не отправлять запрос на каждый символ.

- лёгким;
- быстрым;
- визуально приятным;
- минималистичным;
- без перегруженности формами.

# 30. Важная архитектурная рекомендация

Перед написанием кода сначала изучить существующий проект.

Не создавать новую архитектуру поверх существующей.

Сначала определить:

1. текущую структуру Firebase;
2. существующие коллекции Firestore;
3. текущие типы/модели;
4. существующий routing;
5. существующий UI-kit;
6. существующий способ работы с auth;
7. существующий state management;
8. существующий подход к Firebase queries;
9. существующий способ обработки ошибок;
10. существующий способ работы с env-переменными.

Затем интегрировать «Места» в существующие паттерны проекта.

**Не переписывать существующий код ради этого раздела.**

# 32. Definition of Done

Раздел считается готовым, если:

- пользователь может найти реальное место;
- добавить его на карту;
- отметить как посещённое или желаемое;
- поставить оценки обоим партнёрам;
- записать дату и сумму;
- увидеть место на карте;
- увидеть его в списке;
- открыть полную карточку;
- увидеть историю посещений;
- отсортировать места по рейтингу;
- получить список мест, куда стоит вернуться;
- данные сохраняются в Firebase;
- неавторизованный пользователь не может получить данные;
- существующие разделы приложения продолжают работать;
- интерфейс нормально работает на desktop и mobile.

Главный принцип:

> **Это не карта заведений. Это карта вашей совместной жизни.**
