INITIAL.md — стартовое задание локальному coding-агенту
1. Контекст продукта
Создай адаптивное веб-приложение для двух партнёров, рабочее название — «Вместе». Приложение должно заменить несколько разрозненных списков и таблиц, оставаясь лёгким, приятным и простым в поддержке.
Основные разделы:
1. Дела — задачи, дедлайны, ориентировочная стоимость, отметка выполнения.
2. Идеи — каталог совместных развлечений с описанием, ссылкой, стоимостью, статусом бронирования и случайным выбором одной из подходящих идей.
3. Бюджет — счета/карты/наличные и долги, календарь доходов и планируемых расходов, регулярные операции, прогноз баланса на выбранную дату, фактические расходы и аналитика по месяцам.
4. Ссылки — реестр общих Notion-пространств, документов, таблиц и других полезных URL.
5. Обзор — короткая сводка: ближайшие дела, предстоящие платежи, общий прогнозируемый баланс и предложение развлечения.
Пользователей только двое. Для первого MVP достаточно одной общей учётной записи, которой пользуются оба партнёра. Не делай регистрацию доступной из интерфейса. Аккаунт создаётся вручную в Firebase Console. Данные приватные, внешние посетители не должны иметь к ним доступ.
2. Технологические решения
Используй следующий простой стек, если в репозитории уже нет обоснованного решения, от которого разумнее продолжить:
- React + TypeScript + Vite — клиентское SPA, без отдельного постоянно работающего сервера.
- Tailwind CSS для адаптивной стилизации. Если в репозитории уже настроена совместимая компонентная библиотека, используй её; иначе используй небольшой набор доступных компонентов в духе shadcn/ui/Radix, не превращая проект в огромную систему абстракций.
- React Router для маршрутов основных разделов.
- Firebase Authentication (email/password) для входа.
- Cloud Firestore для данных.
- date-fns с русской локалью для дат.
- lucide-react для единообразных иконок.
- recharts для аналитических графиков.
- react-hook-form + zod для форм и валидации, только если они действительно упрощают реализацию.
- Firebase Hosting для публикации статического приложения.
Не добавляй собственный backend, Express-сервер, Cloud Functions, Redux, ORM, Docker или тяжёлую инфраструктуру без доказанной необходимости. Расчёт прогноза, генерация экземпляров регулярных операций и простая аналитика выполняются на клиенте: для двух пользователей объём данных небольшой.
Проверяй текущий репозиторий до установки пакетов и создания файлов. Не ломай уже настроенную структуру и скрипты. Если Claude Design передал компоненты, токены или прототип, сначала изучи их и используй как визуальный источник истины.
3. Приватность и Firebase
- Вход — email + пароль; в UI есть экран входа, но нет публичной регистрации, сброса пароля можно добавить через Firebase Auth.
- Нельзя считать скрытую кнопку регистрации достаточной защитой. В Firestore Rules разрешай операции только авторизованному UID из allowlist.
- Создай firestore.rules с безопасным deny-by-default поведением. Оставь очевидный placeholder для UID общей учётной записи и задокументируй, как заменить его UID из Firebase Console. Не выкатывай правило, разрешающее доступ всем request.auth != null пользователям.
- Не храни пароль, service account JSON или приватные ключи в клиентском коде или репозитории.
- Firebase Web config может приходить из VITE_FIREBASE_* env-переменных; создай .env.example с названиями переменных и без настоящих значений. Настоящие локальные значения не коммить.
- Клиентские правила должны ограничивать read/write для всех коллекций. По возможности валидируй структуру и базовые типы документов в Firestore Rules; сложные расчёты не перекладывай в правила.
- Не используй Firebase Admin SDK в браузере. Перед деплоем напомни проверить UID allowlist, Firestore Rules и конфигурацию проекта.
Для первого MVP предполагается одна общая учётная запись. Не разрабатывай роли, организации и полноценную multi-tenant архитектуру. Однако код не должен искусственно запрещать добавить второго отдельного пользователя позднее.
4. Принципы продукта и UX
- Язык UI — русский. Денежная валюта по умолчанию — RUB (₽); не добавляй обмен валют.
- Интерфейс адаптивен для телефонов шириной от 360 px, планшетов и desktop.
- Дизайн тёплый, спокойный и минималистичный: тёплый нейтральный фон, графитовый текст, приглушённый зелёный акцент, немного янтарного/терракотового для предупреждений и расходов. Точная палитра определяется по дизайн-файлам, если они есть.
- Не использовать фиолетовые AI-градиенты, стекломорфизм, лишние карточки и чрезмерные тени. Приоритет — иерархия, отступы, читаемость и простые действия.
- На desktop — компактный sidebar: «Обзор», «Дела», «Идеи», «Бюджет», «Ссылки». На мобильном — компактная верхняя панель и удобная нижняя навигация или другое понятное решение без горизонтальной прокрутки страницы.
- Один доминирующий CTA на экран. Второстепенные действия — в меню или панели деталей.
- На телефоне формы открываются в полноэкранной панели или bottom sheet, цели нажатия достаточно крупные.
- Все разделы должны иметь продуманные состояния загрузки, ошибки, пустого списка, сохранения и подтверждения удаления.
- Никаких фиктивных кнопок и пустых заглушек: каждый показанный элемент либо работает, либо явно не входит в MVP и не отображается.
- Используй семантический HTML, доступные подписи полей, видимые focus-состояния и хороший контраст.
5. Функциональные требования
5.1 Дела
Поля задачи:
- title — обязательно;
- description — необязательно;
- dueDate — необязательно;
- estimatedCostMinor — необязательно, стоимость в целых копейках;
- assignee — me, partner или both, необязательно;
- isCompleted — boolean;
- createdAt, updatedAt.
Возможности: создать, редактировать, удалить с подтверждением, отметить чекбоксом выполнение, показать просроченные задачи, сортировать по дедлайну и отделить выполненные. Не добавляй приоритеты, подзадачи и сложные проекты.
5.2 Идеи для совместного досуга
Поля:
- title — обязательно;
- description — необязательно;
- url — необязательно, валидный URL;
- estimatedCostMinor — сумма на двоих, необязательно;
- status — wishlist, booked, completed или archived;
- plannedDate — необязательно;
- createdAt, updatedAt.
Возможности: CRUD, фильтр по статусу, показать стоимость и описание, открыть URL в новой вкладке, менять статус бронирования, архивировать идею и запустить случайный выбор. Рандомизатор должен выбирать только из wishlist, не из уже забронированных/завершённых/архивных записей. Не выбирать случайное значение по результату сортировки или идентификатору: выбор должен быть честно случайным среди доступных элементов. Если доступных идей нет, объяснить это и предложить добавить идею.
5.3 Бюджет: счета и прогноз
Счета:
- name;
- type — debit, credit, cash, savings или other;
- openingBalanceMinor — знаковый баланс на дату фиксации: положительный означает деньги, отрицательный — долг;
- balanceAsOfDate — дата, на которую был зафиксирован начальный баланс;
- createdAt, updatedAt.
Отрицательный баланс кредитной карты отображается как долг, а не как доступные деньги. Общая сумма — нетто-сумма счетов с учётом долгов.
Разовые запланированные операции:
- title, type (income или expense), amountMinor (всегда положительная сумма), date, accountId, category, note;
- status — planned, completed или skipped;
- createdAt, updatedAt.
Регулярные правила:
- те же основные поля, что у планируемой операции;
- frequency — weekly, monthly или yearly;
- startDate, необязательный endDate;
- для ежемесячного события храни желаемый день месяца; если в месяце нет такого дня, используй последний календарный день месяца.
Для отдельных экземпляров регулярного события используй коллекцию recurringOccurrences с ruleId, date, status (planned, completed, skipped) и необязательным actualTransactionId. Это нужно, чтобы отметить оплату конкретного месяца, не отключая весь повторяющийся шаблон.
Прогноз на выбранную дату:
1. Начни с баланса каждого счёта на balanceAsOfDate.
2. Добавь фактические транзакции, которые по дате лежат после исходного снимка баланса и не позже выбранной даты.
3. Добавь планируемые разовые операции, не отмеченные completed или skipped, если их дата попадает в диапазон прогноза.
4. Сгенерируй экземпляры регулярных правил только для рассматриваемого диапазона; включай лишь не пропущенные и не оплаченные экземпляры.
5. Не учитывай завершённую плановую операцию дважды: при отметке как выполненной создай фактическую транзакцию и привяжи её к плановой операции/экземпляру, а прогноз дальше должен брать фактическую запись вместо плановой.
6. Показывай баланс по счетам и общий нетто-баланс на конец выбранного дня, а также список операций, из которых он получился.
Если начальная дата баланса позже выбранной даты, не пытайся выдумывать исторический баланс. Покажи понятную подпись, что прогноз доступен начиная с даты фиксации баланса.
Возможности: добавлять/редактировать/удалять счета, менять начальный баланс и дату его фиксации, добавлять доходы и расходы, задавать повторы, отмечать экземпляр как оплаченный/полученный или пропускать его. Не подключай банковские API и не пытайся синхронизировать реальные карты.
5.4 Фактические доходы и расходы
Храни фактические операции в transactions:
- type — income или expense;
- amountMinor — положительная сумма;
- date;
- accountId;
- category;
- необязательный note;
- необязательные plannedEntryId и recurringOccurrenceId для связи с планом;
- createdAt, updatedAt.
Возможности: добавить, отредактировать и удалить фактическую операцию; быстро выбрать месяц; показать сумму расходов за месяц, расходы по категориям и динамику по месяцам. На графике сравнения используй фактические данные из transactions, фильтруя по type == expense. Если истории мало, честно показывай доступные периоды, не создавай фальшивые точки. Категории должны быть простыми и редактируемыми лишь при реальной необходимости; для MVP можно использовать константный набор: жильё и коммуналка, продукты, транспорт, здоровье, досуг, покупки, подписки, другое.
В аналитике достаточно:
- диаграммы расходов по категориям за выбранный месяц;
- графика общей суммы расходов по месяцам;
- краткого сравнения с предыдущим месяцем, если для обоих периодов есть данные.
Не добавляй финансовые советы, автоматические бюджеты или прогнозирование на основе ML.
5.5 Ссылки
Поля: title, url (обязательно), description, type (workspace, document, spreadsheet, other), tags (необязательно), createdAt, updatedAt.
Возможности: CRUD, поиск по названию/описанию, фильтр по типу, открытие ссылки в новой вкладке с безопасными атрибутами. Не пытайся авторизоваться во внешних сервисах и не хранить их пароли.
5.6 Обзор
Покажи только полезные сводки:
- незавершённые ближайшие задачи;
- ближайшие плановые доходы/расходы;
- общий прогнозируемый баланс на сегодня и ближайшую дату с крупной операцией;
- одну случайно выбранную идею для досуга или кнопку «Выбрать идею».
Обзор — не отдельная аналитическая панель со всеми данными приложения.
6. Архитектура и качество кода
- Раздели UI, доменную логику и доступ к данным. Например: features/, components/, lib/firebase/, lib/finance/, types/ — адаптируй структуру к текущему репозиторию.
- Не разбрасывай вызовы Firestore по компонентам. Используй небольшие typed-сервисы/репозитории и хуки.
- Единообразно обрабатывай loading/error/empty состояния.
- Не делай глобальный state manager, пока достаточно локального состояния и простых контекстов.
- Все денежные значения храни целыми числами в минимальных единицах валюты (amountMinor, для RUB — копейки); пользователь вводит и видит обычные рубли. Форматируй суммы через Intl.NumberFormat('ru-RU', { style: 'currency', currency: 'RUB' }) или эквивалент.
- Не используй денежные значения с плавающей точкой при расчётах.
- Даты сохраняй в однозначном формате (YYYY-MM-DD для календарной даты либо Firestore Timestamp для audit-полей); не допускай сдвига даты из-за UTC-конвертации календарных дней.
- Для повторяющихся правил вынеси расчёт дат в отдельные чистые, тестируемые функции.
- Избегай дублирующих записей при отметке операции как выполненной. По возможности используй Firestore transaction/batch для связанного обновления статуса и создания фактической транзакции.
- Добавь валидацию форм и аккуратные сообщения ошибок на русском.
- Добавь основные unit-тесты чистой финансовой логики и генерации регулярных дат, если тестовая инфраструктура уже есть; если её нет, настрой минимальный Vitest.
- Не делай преждевременную оптимизацию. Подписки realtime используй только там, где они реально улучшают синхронную работу двух устройств; при этом корректно отписывайся от listeners.
7. Данные и UX-детали
- Валюта MVP — RUB. Не делай конвертацию валют.
- Примеры данных могут показывать коммуналку 7 000 ₽ ежемесячно, зарплату, дебетовую карту, кредитную карту с долгом и наличные.
- Не зашивай реальные данные пользователей. Приложение должно начинаться с пустых состояний и предлагать создать первую запись.
- Для дат и подписей используй русскую локаль.
- URL валидируй; не разрешай javascript: и другие небезопасные схемы.
- Удаление важных сущностей подтверждай. Для обычного изменения статуса достаточно undo-toast, если это просто реализовать.
- Если браузер офлайн, не показывай ложное сообщение об успешной синхронизации. Корректно показывай ошибку сохранения или состояние offline.
- Не добавляй уведомления, email-рассылку, PWA, экспорт CSV, импорт банковских операций, несколько домохозяйств, сложные права доступа или вложения в файлы в первую итерацию.
8. Рекомендуемая структура Firestore
Используй верхнеуровневые коллекции:
- tasks
- activities
- accounts
- plannedEntries
- recurringRules
- recurringOccurrences
- transactions
- links
- appSettings (один документ с настройками, если действительно нужен)
В документах храни createdAt и updatedAt, где применимо. Не используй массивы внутри одного общего документа для всех задач/трат/ссылок: отдельные документы упрощают обновления и запросы. Названия коллекций и полей должны быть консистентны.
Если Firestore-запросы требуют индексов, добавь firestore.indexes.json и опиши нужные индексы. Не добавляй индексные комбинации наугад.
9. Этапы реализации
Работай короткими, проверяемыми вертикальными срезами. Не пытайся сгенерировать всю систему за один огромный коммит.
Этап 0 — изучить проект
- Осмотри текущие файлы, package.json, существующий UI, дизайн-токены и инструкции проекта.
- Кратко зафиксируй имеющийся стек и план изменений.
- Не переписывай существующие части, если можно продолжить текущую архитектуру.
Этап 1 — каркас
- Настрой/проверь React, TypeScript, Vite, стили и маршруты.
- Создай дизайн-токены, адаптивный layout, навигацию и экран входа.
- Добавь Firebase init, состояние авторизации, безопасные env-переменные, базовые Firestore Rules и .env.example.
- Реализуй единый паттерн загрузки, ошибок, пустого состояния и диалогов.
Этап 2 — базовые сущности
- Реализуй полный CRUD и все состояния для задач, идей и ссылок.
- Убедись, что чекбоксы, статусы, фильтры, ссылки и случайный выбор работают на реальных данных Firestore.
- Проверь mobile layout.
Этап 3 — бюджетный план
- Реализуй счета, разовые операции, регулярные правила и исключения для отдельных экземпляров.
- Покрой расчёт прогноза и календарную генерацию регулярных дат тестами.
- Реализуй выбор дня, детализацию операций и баланс на конец выбранного дня.
Этап 4 — фактические операции и аналитика
- Реализуй ввод фактических расходов/доходов и безопасную связь с выполненными плановыми событиями.
- Построй диаграмму расходов по категориям и тренд расходов по месяцам.
- Проверь отсутствие двойного учёта фактических и плановых платежей.
Этап 5 — проверка и деплой
- Запусти lint, typecheck, test и production build; исправь обнаруженные ошибки.
- Проверь основные сценарии на desktop, планшете и телефоне.
- Подготовь firebase.json, статический rewrite для SPA и инструкции по Firebase Hosting.
- Не выполняй реальный деплой без явного запроса и без корректной конфигурации проекта.
- Обнови README инструкцией локального запуска, настройки Firebase, настройки UID allowlist, создания единственного аккаунта и деплоя.
10. Definition of Done для MVP
MVP готов, если:
- приложение запускается локально по документированной команде;
- вход работает и неавторизованный посетитель не может читать/писать данные;
- данные сохраняются в Firestore и доступны обоим партнёрам при входе в общий аккаунт;
- задачи, идеи, статусы бронирования и ссылки полностью CRUD-ятся;
- случайный выбор идеи работает и не предлагает забронированные/завершённые элементы;

11. Правила работы агента
1. Сначала изучи репозиторий. Не предполагай, что он пустой.
2. Перед крупным изменением кратко перечисли, что будешь менять и почему.
3. Выбирай самый простой вариант, который выполняет требования; не добавляй фичи «на будущее».
4. Если небольшая неоднозначность не блокирует работу, прими разумное решение и запиши его в README вместо того, чтобы останавливать реализацию.
5. После каждого этапа запускай доступные проверки и исправляй ошибки до перехода дальше.
6. Не заявляй, что тесты или деплой успешны, если реально не запускал их.
7. По завершении сообщи, что реализовано, какие команды были запущены, что требует ручной настройки в Firebase и что пока осталось за рамками MVP.
